## 一、这一步做什么

用户在自己的 CH 专属库 `factor_mid_{拼音}` 里**管理表**（存因子中间值），一步到位覆盖表的增删改查：

- **建表**：列名、列数、类型完全由用户定，后端不预设结构、不限制列数。用户填：表名 + 若干列（列名+类型+注释）+ 引擎 + 排序键 + 主键（可选）。
- **删表**：安全规则——**有数据不让删，想删先清空**。
- **清空**：`TRUNCATE`，清数据保结构。
- **编辑表结构**：可改列注释/类型/列名、加列、删列；**排序键、主键、引擎不可改**（MergeTree 物理基础，前端置灰并说明，要改只能删表重建）。
- **数据预览**：查看表内前 100 行数据 + 总行数，让用户直观看到存了什么。
- **只管理表结构，不写数据**——加载数据是后续独立的第三步。

### 3. `POST /ch-create-table` — 建表

请求体：

```json
{
  "table_name": "my_factor_mid",
  "columns": [
    { "name": "trade_date",   "type": "Date" },
    { "name": "stock_code",   "type": "String" },
    { "name": "factor_value", "type": "Float64", "comment": "因子值" }
  ],
  "engine": "MergeTree",
  "primary_key": ["trade_date"],
  "order_by": ["trade_date", "stock_code"]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `table_name` | string | 是 | 表名，仅字母/数字/下划线，≤63 字符 |
| `columns` | array | 是 | 至少 1 列；每项 `{name, type, comment?}`，name 同上规则，type 必须在 `/ch-types` 白名单内，comment 为可选列注释（自由文本，可空）|
| `engine` | string | 是 | 必须在 engines 白名单内 |
| `order_by` | string[] | 是 | 排序键，非空；每个元素必须是已声明的列名（MergeTree 硬性要求）|
| `primary_key` | string[] | 否 | 主键；**必须是排序键（order_by）的前缀**（同顺序、从头开始的连续子集）。留空则不写 PRIMARY KEY |

成功响应（实测）：

```json
{
  "success": true,
  "message": "表创建成功",
  "data": {
    "database": "factor_mid_zhouxin",
    "table": "my_factor_mid",
    "ddl": "CREATE TABLE `my_factor_mid` (\n  `trade_date` Date,\n  ...\n) ENGINE = MergeTree\nPRIMARY KEY (`trade_date`)\nORDER BY (`trade_date`, `stock_code`)"
  }
}
```

失败时 `{ "success": false, "error": "不支持的列类型: xxx（列 yyy）" }` 等，前端直接展示 `error`。

> 后端已做全部校验（标识符防注入、类型/引擎白名单、排序键/主键必须是已声明列），前端做**基础前置校验**即可（体验更好），最终以后端返回为准。

### 4. `POST /ch-truncate-table` — 清空表数据（保留结构）

请求体：`{ "table_name": "my_factor_mid" }`
成功：`{ "success": true, "message": "数据已清空" }`
失败：`{ "success": false, "error": "..." }`

### 5. `POST /ch-drop-table` — 删除表

请求体：`{ "table_name": "my_factor_mid" }`
成功：`{ "success": true, "message": "表已删除" }`

> **安全规则（后端强制）**：表内**有数据时拒绝删除**，返回
> `{ "success": false, "error": "表内有 N 行数据，请先清空数据再删除表" }`。
> 想删表 → 先「清空数据」→ 再「删除表」。前端可据 `total_rows` 提前提示。

### 6. `GET /ch-table-schema?table_name=xxx` — 读表结构（编辑时回填）

响应：

```json
{
  "success": true,
  "data": {
    "database": "factor_mid_zhouxin",
    "table": "my_factor_mid",
    "columns": [
      { "name": "trade_date",   "type": "Date",    "comment": "",     "in_sorting_key": true,  "in_primary_key": true  },
      { "name": "stock_code",   "type": "String",  "comment": "",     "in_sorting_key": true,  "in_primary_key": false },
      { "name": "factor_value", "type": "Float64", "comment": "因子值", "in_sorting_key": false, "in_primary_key": false }
    ]
  }
}
```

> `in_sorting_key` / `in_primary_key` 标识该列是否属于排序键/主键。前端用它决定**哪些列可删/可改**（属于排序键或主键的列不能删、不能改名/改类型，需置灰）。

### 7. `GET /ch-preview-table?table_name=xxx` — 预览表数据

返回前 **100 行** + 总行数。用**用户自己的 CH 账号**查询。响应：

```json
{
  "success": true,
  "data": {
    "database": "factor_mid_yuyang",
    "table": "ceshi",
    "columns": ["ceshi1", "ceshi2", "ceshi3", "ceshi4"],
    "rows": [
      { "ceshi1": 1, "ceshi2": 100, "ceshi3": 10000, "ceshi4": 1 },
      { "ceshi1": 2, "ceshi2": 200, "ceshi3": 20000, "ceshi4": 2 }
    ],
    "total_rows": 5,
    "limit": 100
  }
}
```

> `columns` 是有序列名数组（用于渲染表头顺序）；`rows` 是对象数组（key=列名）。`total_rows` 是表总行数，`limit` 是本次最多返回行数（100）。当 `total_rows > limit` 时前端应提示"仅显示前 100 行，共 N 行"。空表 `rows: []`。

### 8. `POST /ch-alter-table` — 编辑表结构

请求体：一个 `actions` 数组，按顺序执行；每个 action 一种操作。

```json
{
  "table_name": "my_factor_mid",
  "actions": [
    { "action": "add_column",     "name": "amount",  "type": "Float64", "comment": "成交额", "after": "factor_value" },
    { "action": "modify_comment", "name": "factor_value", "comment": "新的注释" },
    { "action": "rename_column",  "name": "stock_code", "new_name": "symbol" },
    { "action": "modify_type",    "name": "factor_value", "type": "Float32" },
    { "action": "drop_column",    "name": "amount" }
  ]
}
```

action 类型：

| action | 必填字段 | 说明 |
|---|---|---|
| `add_column` | name, type | 加列；可选 `comment`、`after`（插到某列之后）|
| `drop_column` | name | 删列（排序键/主键列不可删，CH 会拒绝）|
| `modify_comment` | name, comment | 改列注释 |
| `rename_column` | name, new_name | 改列名（排序键/主键列改名有限制）|
| `modify_type` | name, type | 改列类型（需类型兼容，否则 CH 报错）|

成功：`{ "success": true, "message": "表结构已更新", "data": { "executed": ["ADD COLUMN ...", ...] } }`
失败：`{ "success": false, "error": "执行失败: ...", "executed": [...已成功...], "failed": "失败的子句" }`

> **不支持修改的项**（前端置灰 + 说明原因）：**排序键（ORDER BY）、主键（PRIMARY KEY）、引擎（ENGINE）**——它们是 MergeTree 的物理存储基础，建表后不可改。要改这些只能「删表重建」。后端不提供对应 action。
>
> **后端二次拦截**：对排序键/主键涉及的列做 `drop_column` / `rename_column` / `modify_type` 时，后端会先查该列是否属于排序键/主键，命中直接返回中文错误（如 `列 stock_code 属于排序键/主键，不能删除…`），而不是把 CH 的英文原始错误抛给用户。前端置灰是第一道、后端拦截是第二道，双保险。改注释（`modify_comment`）对排序键/主键列**允许**，不拦。

const buildAlterActions = () => {
  const actions: any[] = []
  const origByName = new Map(editOriginal.map(c => [c._origName || c.name, c]))
  const currentOrigNames = new Set<string>()

  for (const col of editColumns.value) {
    if (col._isNew) {
      // 新增列
      if (!col.name.trim() || !col.type) throw new Error('新增列必须填列名和类型')
      actions.push({ action: 'add_column', name: col.name.trim(), type: col.type, comment: col.comment?.trim() || undefined })
      continue
    }
    const orig = origByName.get(col._origName!)!
    currentOrigNames.add(col._origName!)
    // 改类型
    if (col.type !== orig.type) actions.push({ action: 'modify_type', name: col._origName, type: col.type })
    // 改注释
    if ((col.comment || '') !== (orig.comment || '')) actions.push({ action: 'modify_comment', name: col._origName, comment: col.comment || '' })
    // 改名（放最后，避免与上面基于原名的动作冲突）
    if (col.name.trim() && col.name.trim() !== col._origName) actions.push({ action: 'rename_column', name: col._origName, new_name: col.name.trim() })
  }
  // 删除：原来有、现在没了的列
  for (const orig of editOriginal) {
    if (!currentOrigNames.has(orig._origName!)) {
      actions.push({ action: 'drop_column', name: orig._origName })
    }
  }
  return actions
}

  }
}

## 六、注意事项

1. **只管理表结构，不写数据**——建表/编辑弹窗都不涉及任何数据加载，那是第三步。
2. **排序键是 MergeTree 硬性要求**，前端已强制"至少选一个排序键"，否则后端会报错。
3. **主键必须是排序键的前缀**（ClickHouse 硬性规则，同顺序、从头连续）。前端已从两方面保证：主键下拉选项只来自已选排序键、提交前再做一道前缀校验；后端 `buildCreateTableDDL` 也会二次校验，非前缀直接返回中文错误。
4. **类型只能选白名单**，不要让用户手输任意类型字符串（后端会拒绝非白名单类型）。
5. **列名/表名规则**：仅字母、数字、下划线（后端 `isSafeIdent` 校验，前端 placeholder 已提示）。
6. IPC 命名沿用第一步的 `myCHXxx` camelCase 风格，与 `myCHStatus`/`myCHInit` 保持一致。
7. **删除表**：后端强制"有数据拒绝删"。前端可先按 `total_rows>0` 提示用户先清空，但最终以后端返回为准（用户可能在别处写过数据，前端 `total_rows` 未必最新）。
8. **编辑表结构**：排序键/主键列的**改名、改类型、删除**——前端置灰是第一道，后端也会拦截返回中文错误（第二道）。**改注释**对所有列（含排序键/主键列）都允许。**排序键/主键/引擎本身不可改**，要调整只能删表重建。
9. **编辑用 diff 提交**：前端把编辑弹窗的改动与打开时的快照对比，生成最小 `actions` 数组；无改动时提示"没有检测到任何修改"。
